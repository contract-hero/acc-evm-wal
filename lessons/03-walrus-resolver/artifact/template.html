Section 1 Storage + the ENS-piggybacked auth gate

The contract you're writing has zero local access-control state. Authorization is borrowed live from the ENS registry on every call.

Two STATICCALLs to the ENS registry per mutation. The contract never stores who the owner is — it always asks.

Section 2 The write path — setWalrusBlob

One external function, three statements. The first one is the load-bearing convention.

Internal-helper auth is a guard rail by convention, not by language feature — but it makes "did I auth this?" answerable from a one-line glance per function.

Section 3 The clear path — clearWalrusBlob

Behaviorally the same as zeroing via setWalrusBlob(node, 0, 0, 0). Semantically — and in event history — different.

Behaviorally equivalent, semantically distinct. The deliberate-clear-vs-accidental-zero distinction is what wallets and explorers render to the user.

Section 4 The read path + ERC-165 declaration

The view is trivial. The detection declaration is where most ENS-adjacent contracts get it wrong.

The detection table

Detecting WalrusResolver in client code

// Don't:  await resolver.supportsInterface(0xbc1c58d1)   // would lie if we'd added it
